## 2. 产品概述

### 2.1 一句话描述

基于 Telegram 的娱乐城：玩家完成邀请绑定与单设备绑定后即可进入游戏厅浏览；首次点击钱包时触发实名认证（姓名、DuitNow、银行户口），审核通过后解锁钱包交易与对局能力。玩家在 **Mini App 网页实时游戏房**内竞标上庄、下注、聊天与抢包；后台发出 TNG 红包领取入口，按实名姓名匹配认额，系统自动计算牌型、输赢与账务。Telegram Bot **仅负责入口与私聊通知**。

### 2.2 核心价值

- 准入可控：注册只强制邀请关系与一账号一设备；实名 + 银行户口在首次访问钱包时触发。
- 对局在网页房：竞标、下注、撤回、聊天、抢包、成绩单均在 Mini App 实时游戏房完成。
- 认额可靠：以发包账号领取明细为准（实名姓名匹配 + 后台确认），不依赖玩家口头报数。
- 账务清晰：赌资账与红包备付账分离；中奖金额系统计算。
- 运营可配：推送、倍数/抽水、红包脚本、多 Bot 入口切换。

### 2.3 系统组成

```
玩家侧：Telegram Bot 私聊（入口/通知）+ Mini App 游戏厅与网页游戏房 + TNG eWallet
你们侧：业务 API + WebSocket 房间中心 + 局/结算引擎 + 推送服务 + 运营管理后台 + PostgreSQL/Redis
外部：Telegram Bot API、TNG eWallet（Money Packet 链接，App 内创建；无对外 API）
```

## 3. 总体架构需求

### 3.1 逻辑架构

1. **Telegram Bot**：`/start`、深链邀请参数、菜单按钮「进入游戏厅」、私聊推送（实名/奖励/公告/充提）。**不解析群指令、不群禁言、不在群内播报成绩单。**
2. **Mini App（游戏厅）**：准入流程 + 四 Tab 主界面 + 玩法介绍 + **网页实时游戏房**（WebSocket）。
3. **业务 API**：鉴权、用户、设备、KYC、钱包、房间、对局、结算、推送、TNG。
4. **局引擎 / 结算引擎**：阶段状态机、倒计时、冻结/解冻、牌型计算、中奖计算、抽水。
5. **管理后台**：审核、推送、配置、红包脚本、网页房管理、对局监控、多 Bot、财务对账。
6. **数据层**：PostgreSQL（持久化）+ Redis（局状态/锁/倒计时）+ 队列（推送/回调处理）。

### 3.2 多 Bot 要求

- 支持配置多个 Telegram Bot（token、username、启停、默认 Bot）。
- 推送、Webhook、`initData` 验签均按 `bot_id` 路由。
- 房间绑定具体 Bot；用户记录 `last_bot_id` 用于私聊触达。
- 后台可更换默认入口 Bot，不影响已有钱包与对局历史数据。

### 3.3 环境与安全（基线）

- Mini App / 后台全站 HTTPS。
- Telegram `initData` 必须服务端校验签名与时效。
- Bot token、TNG 密钥加密存储；后台敏感操作审计日志。
- 账务流水幂等（防重复回调/重复结算）。

玩家进入 Mini App 后，只需完成邀请人与设备绑定即可进入四 Tab 主界面；注册阶段不强制实名认证。

```
打开 Mini App
```

### 4.4 推广返水体系（我的推广 / 邀请好友）

采用「3 层返水模式」：绑定邀请人后形成推广关系，层层返利；返水按「有效下注」计算，比例后台可配。

#### 4.4.1 返水层级与默认比例

以「拿返水的人」视角：

| 层级 | 说明 | 默认返水比例 |
|---|---|---|
| 自身游戏奖励（第 3 层） | 玩家可获取自己有效下注的返水 | 0.7% |
| 直属下线（第 2 层） | 可抽取我直接邀请的下级的有效下注返水 | 0.5% |
| 下线会员/二级（第 1 层） | 可抽取下级的下级的有效下注返水 | 0.3% |

层级关系示例（对应宣传图）：

```
案例一：代理A → 代理B
  A 抽取 B 有效下注的 0.5%；B 获得自己有效下注的 0.7%

案例二：代理A → 代理B → 玩家C
  A 抽取 C 有效下注的 0.3%；B 抽取 C 有效下注的 0.5%；C 获得自己的 0.7%

层级延伸：A → B → C → D
  A 无法抽取 D 的返水（最多向下两级）；B 仍可抽取 D 的 0.3% 层级返水
```

规则要点：

1. **只计「有效下注」**，无效下注不计入返水（口径见 4.4.1a）。
2. 返水按层级关系**系统自动结算，每日结算、实时发放**。
3. 返水比例如有调整，平台另行公告（后台改配置 + 发公告推送）。
4. 向上追溯最多两级，超过两级不产生返水。

#### 4.4.1a 「有效下注」口径（已确认）

| 角色 | 有效下注定义 |
|---|---|
| 闲家 | 本局**参与结算**的下注金额（输、赢均计入） |
| 庄家 | **不按庄钱/竞标金额计算**；按本局与闲家实际对赌结算的下注总额计入（即所有参与结算闲家的下注之和），**庄家输赢均计返水** |

不计入有效下注（无效下注）：

- 发 `0` 撤回的下注  
- 取消局（无人上庄/无人下注/链接失效等）中被退回的金额  
- 弃权未下注  
- 平局退回的该笔对局注码（默认不计，后台可开关）  
- 竞标庄钱本身（仅作坐庄资格与庄池，不产生返水基数）

## 5. 游戏需求 — 至尊牛牛

### 5.1 游戏简介

至尊牛牛基于 Touch n Go eWallet 红包链接的多人对战玩法。  
每局由一位玩家竞标庄钱做「庄家」，闲家自由下注；系统统一发出 TNG 红包链接；按抢到金额识别点数/牌型并比对庄闲；胜者按倍数赢取筹码；平台抽取小额抽水。

### 5.2 在哪里玩

- 产品上只有 **一个游戏：至尊牛牛**，不是多牌桌列表。
- 对局在 Mini App 的 **「至尊牛牛互动群」**（网页群聊界面）内进行，看起来像群组，但不是 Telegram 群。
- 玩家路径：Telegram Bot → 进入游戏厅 → 大厅点「至尊牛牛」或消息页点「互动群」→ 进入群聊对局。
- 竞标、下注、撤回、群聊天、抢包、成绩单均在该网页互动群完成。
- Telegram Bot 只负责入口与私聊通知；真正的 Telegram 群不作为对局场地。

### 5.3 角色

| 角色 | 规则 |
|---|---|
| 庄家 | 竞标最高价上庄；庄钱冻结为「庄池」；承担所有已下注闲家输赢；赔付上限=庄池 |
| 闲家 | 非庄家可下注；不下注视为本局弃权，不参与结算 |

### 5.4 对局状态机

```
WAITING（大厅凑人，达最低人数自动开下一局）
  → BANKER_BID（竞标庄钱倒计时）
      ├ 无人出价 → CANCELLED
      └ 最高价中标 → 冻结庄池
  →（可选）续庄：竞标中标局可沿用庄钱续一次；连续坐庄最多两局
  → BETTING（闲家下注倒计时）
      ├ 无人下注 → CANCELLED（庄池全额退回）
      └ 有下注 → 冻结闲家注码
  → SENDING_PACKET（后台红包脚本控制发包）
  → CLAIMING（庄家 + 已下注闲家抢包；后台认额录入/确认）
      ├ 链接异常/失效 → CANCELLED（冻结原路退回）
      └ 认额完成或按超时规则处理
  → SETTLING（算牌型、比对、算中奖、抽水、写账）
  → FINISHED → 询问续庄 → 下一局
```

### 5.5 阶段细则

#### 5.5.1 大厅阶段

- 玩家进入对应群组房间等待。
- 系统在凑够最低开局人数后自动开启下一局。

#### 5.5.2 上庄 · 竞标庄钱

| 编号 | 需求 | 说明 |
|---|---|---|
| G-BID-01 | 竞标方式 | 倒计时内（默认 30 秒）全体玩家在游戏房发送金额数字；再次发送=修改最终报价 |
| G-BID-01a | 出价播报 | 每次出价后小助手 @ 该玩家播报金额与当前最高，并追问「还有没有更高」 |
| G-BID-01b | 收官确认 | 出价窗口结束后播报全员出价名单，再依次各发 3、2、1，然后锁定最高有效价 |
| G-BID-02 | 中标规则 | 最高有效出价者成为庄家，金额冻结为庄池 |
| G-BID-03 | 续庄 | 结算完成后仅允许紧邻上一局庄家在倒计时内确认；沿用上一局庄钱。每次竞标中标后最多续一次（连续最多两局）；第三局强制公开竞标，上一任庄家仍可参与，若最高有效价中标则开启新的续庄资格 |
| G-BID-04 | 无人竞标 | 本局取消，不进入下注 |
| G-BID-05 | 余额不足 | 拒绝竞标并提示；不扣款 |

#### 5.5.3 下注阶段

| 编号 | 需求 | 说明 |

| G-BET-01 | 参与者 | 除庄家外的玩家 |
| G-BET-02 | 动态范围 | **已确认公式**：下注上限 = 庄钱 × 0.5%，梭哈上限 = 庄钱 × 5%（下限固定：下注 2 / 梭哈 20）；再按人数修正——**人数少则调高比例**（人数系数表后台配置）。示例：庄钱 5000 → 下注 2~25 / 梭哈 20~250；庄钱 10000 → 下注 2~50 / 梭哈 20~500。目的：防止玩家「喝水」（总注超出庄池赔付能力） |
| G-BET-03 | 未下注 | 弃权，不赢不输 |
| G-BET-04 | 下注指令 | 普通下注：直接发送金额数字 |
| G-BET-04a | 梭哈指令 | 梭哈：发送「`sh金额`」（如 `sh300`），金额须在梭哈范围内 |
| G-BET-05 | 撤回 | **已确认上线**：封盘前发送 `0` 撤回本局下注，冻结金额即时解冻退回 |

| G-BET-08 | 成功 | 金额从余额冻结 |

#### 5.5.4 系统发包（后台脚本控制）

| 编号 | 需求 | 说明 |
|---|---|---|
| G-PKT-01 | 脚本归属 | 红包发送由**管理后台红包脚本**控制，不由群内玩家触发创建 |
| G-PKT-02 | 模式 | 支持自动发包 / 半自动（待运营确认后发送） |
| G-PKT-03 | 统一发送 | 系统将 TNG 红包链接发到游戏群；禁止玩家私自分享或冒充系统链接 |
| G-PKT-04 | 领取动作 | 用户点击链接/按钮 → 跳转 TNG eWallet 领取（方案 A） |
| G-PKT-05 | 抢包资格 | **仅本局参与者可抢**：庄家 + 已下注的闲家；未下注用户点击不提供领取入口（系统侧校验资格后才展示/下发领取链接） |

#### 5.5.5 抢额识别

**TNG 能力调研结论（2026-08）：**

1. TNG「Money Packet」是消费者功能：在 TNG App 内创建红包，生成链接/QR 可分享至 Telegram 等渠道，领取者获得随机金额；**官方未提供创建红包的 API，也没有「谁领了多少」的对外回调**。
2. TNG 商户/Mini Program Open API（`/v1/payments/pay` + `notifyPayment` webhook）只覆盖「用户向商户付款」场景，不适用于向用户发红包。
3. 发包账号可在 TNG App 内「Money Packet → History」查看每个红包的领取明细（领取人 TNG 显示姓名 + 金额）；领取者必须是完成 eKYC 的 TNG 用户。

**因此认额采用「发包账号明细 + 实名姓名匹配」机制**（这也是实名认证要求玩家姓名与 TNG 头像姓名完全一致的原因）：

| 编号 | 需求 | 说明 |
|---|---|---|
| G-CLM-01 | 认额来源 | 发包 TNG 账号内该红包的领取明细（领取人姓名 + 金额） |
| G-CLM-02 | 用户映射 | 领取人 TNG 姓名 ↔ 平台实名姓名匹配到 user_id；姓名即玩家 TNG 电子账号的身份锚点 |
| G-CLM-03 | 录入方式 | 后台「认额录入」页：运营对照发包账号明细逐笔录入/确认；系统按姓名自动预匹配，人工确认后生效 |
| G-CLM-04 | 幂等 | 同一局同一玩家只认额一次；重复录入拦截 |
| G-CLM-05 | 用途 | 认额金额仅用于计算点数/牌型，**不直接作为游戏输赢入账金额** |
| G-CLM-06 | 超时处理 | 由后台操作：可取消本局（冻结原路退回）、判未抢者弃权、或人工补录后继续结算 |
| G-CLM-07 | 姓名冲突 | 同名玩家或姓名匹配失败时，后台人工指定归属（记审计） |
| G-CLM-08 | 接口预留 | 认额模块抽象为 provider 接口；未来若接入具备领取回调能力的通道，可切换为自动认额，不改结算引擎 |

#### 5.5.6 结算与中奖金额（系统计算）

系统逐个比对庄家与闲家牌型/点数，**中奖与输赢金额全部由系统计算**，写入结算单与钱包流水。

| 场景 | 计算规则 |
|---|---|
| 闲家赢 | 应付 = 倍数 × 闲家下注；闲到账 = 应付 − 闲赢抽水（默认 5%）；从庄池支付 |
| 闲家输 | 闲家下注全数归庄；平台从庄家本局该笔盈利抽水（默认 5%） |
| 牌型/结果导致庄赢闲输（含同点规则见下） | 按上「闲家输」 |
| 完全平局（等级相同且红包金额完全相同） | 该对不结算，双方相关下注原路返回 |
| 庄池不足 | 以庄池余额为赔付上限，不足部分免赔；结算单标注免赔额 |
| 庄家盈利抽水 | 从庄家盈利中抽取（默认 5%） |
| 局结束庄池剩余 | 退回庄家可用余额 |

**抽水规则（已确认）**：抽水 5% **只抽赢方的盈利**——闲家赢抽闲家盈利的 5%，庄家赢抽庄家该笔盈利的 5%；输方不重复抽。抽水与庄家三项费用（上庄费/服务费/代包费，见 5.11.4）**并存**。

**展示**：群内结算播报 + 钱包明细 +（可选）Bot 私聊。

### 5.6 点数计算

1. 取红包金额（含小数点后两位）的全部数字相加。  
2. 取个位数为「点数」。  
3. 例：`3.42` → 3+4+2=9 → 9 点。  
4. 总和个位为 0 时显示为 **10 点**（牛牛最大点数）。

### 5.7 牌型与倍数（由高到低）

实际倍数以后台配置为准，与游戏内显示实时同步。默认如下：

| 牌型 | 默认倍数 | 定义 | 示例 |
|---|---|---|---|
| 豹子 | 17 | 三位非零相同数字 | 1.11 / 7.77 / 9.99 |
| 满牛 | 15 | 整数金额 | 1.00 / 5.00 / 88.00 |
| 反顺 | 14 | 三位数字严格递减 | 9.87 / 3.21 / 2.10 |
| 顺子 | 13 | 三位数字严格递增 | 0.12 / 1.23 / 7.89 |
| 对子 | 12 | 后两位相同且非零 | 1.22 / 7.55 |
| 金牛 | 11 | 仅一位非零数字 | 0.10 / 0.50 |
| 普通 | 按 1–10 点倍数 | 后台配置点位倍数 | — |

**已确认：全部牌型倍数（含普通 1–10 点各点位倍数）、抽水比例均在管理后台自定义修改，保存后新局生效，游戏内展示实时同步。**

### 5.8 牌型比较规则

1. 先比牌型等级：豹子 > 满牛 > 反顺 > 顺子 > 对子 > 金牛 > 普通。  
2. 等级不同：高等级胜。  
3. 等级相同：比红包金额，金额大者胜。（例：2.80 赢 1.09，即便同为 10 点）  
4. 等级相同且金额完全相同：平局，该对不结算，下注原路返回。  
5. **补充实现约定（待产品最终确认写入配置）**：普通牌型之间若需「先比点数再比金额」，以后台「比较策略」开关为准；默认按本节第 3 条（同级直接比金额）。

### 5.8a 自爆规则（已确认）

**点数不超过 3 点（1/2/3 点，普通牌型）即「自爆」，直接判输**，不进入比牌；成绩单以 💥 标记。

| 情形 | 处理 |
|---|---|
| 闲家自爆 | 该闲家直接判输，下注归庄（按「闲家输」结算） |
| 庄家自爆 | **庄家 3 点及以下同样自爆**：直接输给所有未自爆的闲家，按各闲家牌型倍数从庄池赔付 |
| 庄闲双方均自爆 | **已确认：算庄家赢**（闲家输，下注归庄） |
| 特殊牌型豁免 | 金牛等特殊牌型即使数字和的点数低，默认**不判自爆**（以牌型等级优先；后台开关可调） |

自爆阈值（默认 ≤3 点）为后台可配置项。

#### 5.11.2 成绩单（每局，核心需求）

结算完成后小助手公布本局成绩单，要求：

1. **标注局号**：成绩单可追溯是第几局（对应后台结算单）。
2. **逐玩家明细，必须 @ 出来**，每行包含：
   - `@玩家` 抢到金额、下注类型与金额（下注 X / 梭哈 X）
   - 结果：→ 赢 X / → 输 X / 平
   - 特殊标记：**自爆**（💥 标记）等特殊结果需显式标出
   - 积分滚动：上局:X 本局:Y（上局结余 → 本局结余）
3. **庄家汇总段**（分隔线以下）：
   - `庄家（@xxx）` 抢到金额 + 点数/牌型
   - 对局统计：输 X 家 / 赢 X 家 / 平 X 家
   - 费用明细：上庄费、服务费、代包费（逐项列出，负数展示）
   - **庄盈利/庄亏损**：本局庄家净结果（如「庄亏损 -1271.47」）
   - 上庄积分（本局庄池）与 **庄总积分**（庄家累计积分/总盈利记录）
   - **庄家走势**：最近 N 局庄家牌型/点数序列（如「9点 → 反顺 → 10点 → 1点 → 7点 → 6点 → 对子 → …」）

> 成绩单数字必须与后台结算单完全一致；庄家总盈利与走势由系统持久化记录（见数据实体 banker_stats）。

#### 5.11.3 群秩序与状态控制

| 编号 | 需求 | 说明 |
|---|---|---|
| G-CTL-01 | 阶段禁言 | 抢红包阶段网页房输入框禁用聊天（提示「抢红包阶段请专注领取」）；竞标/下注通过房内操作区提交 |
| G-CTL-02 | 状态条 | 常驻展示：当前阶段与倒计时、下注/梭哈范围、自动认尾包开/关、24 小时内已玩局数 |
| G-CTL-03 | 浮层入口 | 排行榜、每日奖励等固定入口（群内侧边悬浮） |
| G-CTL-04 | 文案可配 | 以上所有播报文案模板均在后台可编辑 |

#### 5.11.4 庄家费用（已确认公式，后台可配）

庄家结算时除输赢外，逐项收取以下费用：

| 费用 | 计算规则（已确认） | 示例 |
|---|---|---|
| 上庄费 | **庄钱（上庄积分）× 1%**（比例后台可调） | 庄钱 5000 → 上庄费 50；庄钱 7776 → 77.76 |
| 服务费 | **每场固定金额**，后台自设，全场统一 | 38.00 / 场 |
| 代包费 | **等于本局 TNG 红包总额**，红包总额按参与人数 × 人均单价计算（单价后台可配） | 30 人 → 发 TNG 红包 31.2 → 代包费 31.2 |

- 三项费用均由庄家承担，从庄家结算中扣除。
- 代包费用于覆盖平台代发 TNG 红包的备付成本（与红包备付账勾稽）。
- 费用逐项写入结算单与流水，成绩单展示必须一致。
- 此前「抽水 5%」与上述费用的关系：以后台费用配置为准，二者可并存或替代（剩余待确认，见 Q13a）。

## 6. 账务需求（必须算清）

### 6.1 两本账分离

| 账本 | 内容 | 说明 |
|---|---|---|
| 赌资账 | 可用余额、庄池冻结、下注冻结、输赢结算、抽水 | 玩家中奖/亏损只走这里 |
| 红包备付账 | 备付金拨出、TNG 在途、领取核销、异常损失 | 记录打进 TNG 的红包成本 |

**认额金额只用于牌型，不直接计入玩家游戏输赢。**

### 6.2 科目（逻辑）

- 玩家可用余额  
- 玩家冻结-庄池  
- 玩家冻结-下注  
- 平台抽水账户  
- 平台红包备付金  
- TNG 在途  
- 奖励账户  
- 返水佣金账户（推广返水支出）  
- 调账过渡  

### 6.3 记账原则

1. 任何余额变动必须写 ledger，禁止只改余额字段。  
2. 先冻后结；取消局原路解冻。  
3. 结算、认额录入必须幂等。  
4. 每局生成不可篡改「结算快照」（配置、认额、分录引用）。  
5. 人工调账必须有操作者、原因、审批（按权限）。

### 6.4 中奖金额

- 全部由结算引擎按 5.5.6 计算。  
- 玩家、客服、财务均以结算单为准。  
- 网页房成绩单展示的中奖数字必须与结算单一致。

## 10. 验收标准（摘要）

1. 新用户经邀请链接进入，邀请人 UID 自动填入并可完成绑定。  
2. 完成邀请人和设备绑定后，即使未实名也能进入四 Tab 主界面；首次点击钱包会跳转实名认证。  
3. 未实名不能进行钱包交易、竞标、下注或抢包；实名表单仅含姓名与 DuitNow，银行卡在提现账户中另行添加。  
4. 一账号第二台设备无法直接绑定，需后台解绑。  
5. 完整跑通：竞标 → 下注 → 后台发包 → TNG 跳转领取 → 后台认额录入（姓名匹配）→ 系统算出中奖并入账。  
6. 取消局、无人上庄、无人下注、链接失效均正确退款。  
7. 庄池不足时免赔计算正确且可在结算单核对。  
8. 后台可发送公告/奖励类推送到 Bot 私聊。  
9. 可添加并切换另一 Telegram Bot，验签与推送仍正确。  
10. 赌资流水与红包备付台账可对上；无「只改余额无流水」。  
11. 每个用户在「邀请好友」页有专属二维码；好友扫码或输 UID 均可绑定；绑定后形成两级推广关系。  
12. 「我的推广」页正确展示三级返水比例、当日佣金、三类流水与邀请统计；佣金按日结算入账且有流水记录。  
13. 实名通过后必须设置支付密码；未设置、错误或锁定时，提现与发送群红包均不能产生资金分录。  
14. 相同 requestId 的提现或群红包重放只返回原结果，不重复扣款或重复发送群聊红包卡片。  
15. 后台重置支付密码后旧设备会话立即失效，玩家重新绑定设备并设置新密码后才可进行资金转出。
