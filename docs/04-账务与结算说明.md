# 至尊牛牛 — 账务与结算说明

> 对应 PRD：`01-产品需求文档-PRD.md` 第 6 章。  
> 供开发实现结算引擎、财务对账与测试用例使用。

---

## 1. 设计原则

1. **两本账分离**  
   - 赌资账：竞标、下注、输赢、抽水、奖励、调账  
   - 红包备付账：打入 TNG 的红包本金、在途、核销、损失  
2. **认额 ≠ 中奖**  
   - 认额金额（后台对照发包账号明细录入确认）只用于算点数/牌型  
   - 玩家到账金额只来自结算单（系统计算）  
3. **先冻后结**；取消局原路退回  
4. **每笔变动写 ledger**；认额录入与结算必须幂等  
5. **每局结算快照不可篡改**

## 4. 分录模板

以下金额单位为 RM；抽水只抽赢方盈利（默认闲赢 3%、庄赢 5%），与庄家三项费用并存。完整公式见《06-公式与数值配置总表》。

### 4.1 庄家中标（庄池 100）

| 科目 | 变动 |
|---|---|
| USER_AVAILABLE（庄家） | −100 |
| USER_FREEZE_BANKER（庄家） | +100 |

### 4.2 闲家下注 10（本局最高赔付倍数 17）

| 科目 | 变动 |
|---|---|
| USER_AVAILABLE（闲家） | −170 |
| USER_FREEZE_BET（闲家） | +170 |

冻结额为最大赔付预留金 `10 × 17 = 170`，下注本金仍记录为 10。若余额不足，系统在下注时先自动降低实际接受金额。

梭哈单固定 1:1，本笔赔付倍数为 1：梭哈 100 时 `USER_AVAILABLE −100`、`USER_FREEZE_BET +100`，因此可精确到分押上全部可用余额。

### 4.3 后台脚本创建红包（总额 50）

| 科目 | 变动 |
|---|---|
| PLATFORM_RESERVE | −50 |
| TNG_TRANSIT | +50 |

### 4.4 认额确认领取 3.42

| 科目 | 变动 |
|---|---|
| TNG_TRANSIT | −3.42 |

同时写 `claims.amount = 3.42`（**不**增加玩家 USER_AVAILABLE）。

### 4.5 闲家赢（倍数 12，下注 10）

```
应付 payable = 12 × 10 = 120
抽水 rake = 120 × 3% = 3.6
闲到账 win_net = 116.4
```

推荐分录顺序：

1. 解冻闲家最大赔付预留 170：`USER_FREEZE_BET −170` → `USER_AVAILABLE +170`
2. 庄池支付闲家净赢 116.4：`USER_FREEZE_BANKER(庄) −116.4`，`USER_AVAILABLE(闲) +116.4`。
3. 同一笔应付内划抽水 3.6：`USER_FREEZE_BANKER(庄) −3.6`，`PLATFORM_RAKE +3.6`。

净效果：闲家可用 +116.4（相对开局）；庄池减少 120。

若庄池仅剩 80（不足 120）：

```
实付 paid = 80
免赔 shortfall = 40
抽水按实付计算：rake = 80 × 3% = 2.4
闲到账 = 77.6
结算单标注 shortfall=40
```

### 4.6 闲家输（下注 10，庄家金牛 11 倍）

1. 理论应赔 `10 × 11 = 110`；从 `USER_FREEZE_BET(闲)` 划 `104.5` 至庄家庄池、划 `5.5` 至 `PLATFORM_RAKE`。
2. 未使用预留 `170 − 110 = 60`：`USER_FREEZE_BET(闲) −60` → `USER_AVAILABLE(闲) +60`。

净效果：闲家失去 110；庄家该笔净得 104.5；抽水 5.5。

### 4.6a 梭哈单（固定 1:1）

梭哈 100、预留 100：

- 梭哈赢（无论豹子还是普通点数）：应付 `1 × 100 = 100`，抽水 `100 × 3% = 3`，闲到账 97；庄池减少 100。
- 梭哈输（无论庄家什么牌型）：应赔 `1 × 100 = 100`，从 `USER_FREEZE_BET(闲)` 划 95 至庄池、划 5 至 `PLATFORM_RAKE`，预留刚好用尽、无退回。
- 庄池不足时梭哈与普通下注同队排序（按牌型倍数 → 点数 → 红包金额 → 下注时间），实付不足记 `shortfall`。

### 4.7 平局（该对）

`USER_FREEZE_BET(闲) −170` → `USER_AVAILABLE(闲) +170`
庄池不动。

### 4.7a 庄家费用（上庄费 / 服务费 / 代包费）

已确认公式（比例/单价后台可配）：

| 费用 | 公式 | 示例 |
|---|---|---|
| 上庄费 | 庄钱 × 1% | 5000 → 50；7776 → 77.76 |
| 服务费 | 每场固定 | 38.00 |
| 代包费 | = 本局 TNG 红包总额 = 参与人数 × 人均单价 | 30 人 × 1.04 = 31.20 |

结算时向庄家逐项收取：

| 科目 | 变动 |
|---|---|
| USER_FREEZE_BANKER 或 USER_AVAILABLE（庄家） | −各项费用 |
| PLATFORM_RAKE（或独立费用科目 PLATFORM_FEES） | +各项费用 |

- 每项费用独立一条 ledger（ref_type = `fee_banker_seat` / `fee_service` / `fee_packet_agent`）。
- 代包费与红包备付账勾稽：庄家支付的代包费应覆盖 PLATFORM_RESERVE 拨出的红包总额。
- 成绩单逐项展示，必须与流水一致。

### 4.8 局结束退还庄池剩余

`USER_FREEZE_BANKER(庄) −剩余` → `USER_AVAILABLE(庄) +剩余`

### 4.9 取消局（任意阶段失败/无人下注等）

- 所有 `USER_FREEZE_*` → 对应玩家 `USER_AVAILABLE`  
- 若已 `packet_create`：TNG_TRANSIT 未核销部分转「红包异常/损失」处理，不得静默抹账  

### 4.10 每日牌型王奖励 188.88

`PLATFORM_REWARD −188.88` → `USER_AVAILABLE +188.88`  
并触发推送。

### 4.10a 推广返水日结（示例）

有效下注口径：

- 闲家：参与结算的下注金额（输赢均计）。
- **庄家：不按庄钱计；按该局对赌结算的闲家下注总额计，输赢均计。**
  例：庄家坐庄一局，3 个闲家分别下注 10 / 20 / 30 并全部结算 → 庄家该局有效下注 = 60（无论庄输庄赢）。
- 不计：撤回（发 0）、取消局退回、弃权、竞标庄钱本身；平局默认不计（开关）。

某玩家某日：自身有效下注 1000、直属下线 2000、二级下线 500；比例 0.7% / 0.5% / 0.3%。

```
佣金 = 1000×0.7% + 2000×0.5% + 500×0.3% = 7 + 10 + 1.5 = 18.50
```

| 科目 | 变动 |
|---|---|
| PLATFORM_REBATE | −18.50 |
| USER_AVAILABLE（该玩家） | +18.50 |

ref_type = `rebate`；`rebate_settlements` 记录三级流水基数与比例快照；同日同人只结一次（幂等）。

### 4.11 人工调账 +50

`ADJUST_CLEARING −50` → `USER_AVAILABLE +50`  
记 operator_id 与原因。

### 4.12 提现与手续费

提交提现时，申请总额先从 `USER_AVAILABLE` 转入 `USER_FREEZE_WITHDRAW`。

- 审核通过：实际到账金额转入 `ADJUST_CLEARING`；手续费单独转入 `PLATFORM_FEES`。
- 审核驳回：申请总额原路退回 `USER_AVAILABLE`。
- 用户工单必须同时展示申请总额、手续费和实际到账金额。
- 历史订单没有手续费快照时按手续费 0 处理。

### 4.13 用户发起资金请求的幂等规则

- 打赏、充值申请、提现申请、玩家群红包都必须携带客户端生成的 `requestId`。
- 网络超时后重试必须复用同一个 `requestId`，服务端返回第一次处理结果，不得再次扣款或创建工单。
- 待确认 `requestId` 按用户隔离持久保存在客户端；关闭并重开 Telegram WebView 后仍须复用，收到成功或明确冲突后才清除。
- 同一个 `requestId` 若对应不同金额、账户或业务信息，必须拒绝并返回 `IDEMPOTENCY_CONFLICT`。
- 所有 ledger 幂等键重放时必须校验金额、科目、方向和业务关联完全一致。

### 4.14 支付密码与资金出账门禁

- 提现及玩家发送群红包前，服务端必须验证六位支付密码；仅有前端弹窗不构成安全门禁。
- 支付密码使用账号隔离的 HMAC 材料再进行 bcrypt 哈希；明文不得落库、写日志或进入账务备注。
- 连续错误 5 次锁定 15 分钟；正确验证后清零失败次数。
- 新资金请求顺序：校验业务参数 → 查询 `requestId` 重放 → 验证支付密码 → 创建业务单 → 写双分录。
- 已成功请求的相同 `requestId` 重放直接返回原结果，不再次验密、不重复扣款；业务参数不同则返回 `IDEMPOTENCY_CONFLICT`。
- 验密、改密、重置及资金事务通过支付凭证行锁串行化；资金事务必须再次确认验密时的单调版本。
- 后台重置将凭证标记为未设置并递增版本，不删除版本历史；重设后继续递增，旧验密结果永不重新有效。
- 后台重置支付密码必须填写原因、写审计日志，并同时解绑设备及使旧设备 JWT / WebSocket 失效。

### 5.4 成绩单展示修订不属于财务调账

`Settlement`、`LedgerEntry`、钱包余额以及 `RoundScoreboard.playerLines / bankerSummary` 是不可变的真实结算依据。运营中心的成绩单编辑只写入独立的版本化展示配置，可调整标题、展示名、逐行备注、庄家备注和页脚说明。

强制约束：

1. 展示接口使用严格字段白名单，不接收金额、输赢、牌型、点数、抽水或余额字段。
2. 保存展示修订不得调用钱包转账、冻结/解冻、结算重算或流水写入。
3. 每次修改保存原因、管理员、前后修订号与渲染快照，并写入审计日志和牌局事件。
4. 恢复历史展示版本会创建新的修订，不覆盖旧历史。
5. 数据库修订先提交、消息同步后执行；Redis 锁不可用或小助手同步失败只影响展示同步状态，不得丢失展示修订，更不得回滚或改写真实结算，可由运营重试。
6. 若原聊天消息已超过 7 天保留期，只标记消息过期，不把旧成绩单重新发送到当前群聊。
7. 原始结算展示保存为可恢复的 `v0`；运营预览额外展示应赔、实赔、免赔、抽水、庄家毛输赢及费用时，数据仍只读取结算快照。

如需更正真实金额或余额，必须走独立的财务调账流程并产生双边流水；禁止以“编辑成绩单”代替调账。

## 6. 中奖金额计算伪代码

闲家赢的赔付**不按下注顺序**，而是先把本局全部赢家排队后依次从庄钱扣减：

```text
function payoutQueue(winners):
  # 倍数高 → 点数大 → 红包金额大 → 下注时间早
  return sortBy(winners, [-handRank, -points, -claimCents, +betPlacedAt])

for w in payoutQueue(winners):
  w.paid = min(w.payable, potLeft)       # 庄钱不足 → 剩余全给他
  w.shortfall = w.payable - w.paid       # potLeft 为 0 时全额记免赔 = 喝水
  potLeft -= w.paid
```

```text
function settlePlayer(bankerClaim, playerClaim, bet, potLeft, cfg):
  cmp = compareHands(bankerClaim, playerClaim, cfg)
  if cmp == TIE_SAME_AMOUNT:
    unfreeze(player.bet)
    return { outcome: TIE, paid: 0, rake: 0 }

  if cmp == PLAYER_WIN:
    mult = multiplierOf(playerClaim, cfg)  # 以胜方牌型倍数为准（若规则要求用闲家牌型）
    payable = mult * bet
    paid = min(payable, potLeft)
    shortfall = payable - paid
    rake = paid * cfg.player_win_rake_rate
    credit player (paid - rake)
    potLeft -= paid
    return { outcome: WIN, payable, paid, shortfall, rake, potLeft }

  if cmp == BANKER_WIN:
    transfer bet to banker pot
    rake = bet * cfg.banker_win_rake_rate
    deduct rake from banker gain
    return { outcome: LOSE, paid: 0, rake, potLeft }
```

> 胜方倍数取值（闲家牌型 vs 庄家牌型）若业务有特殊规定，在配置中明确；默认使用**闲家自身牌型倍数**计算闲赢赔付。

## 7. 对账日报（财务）

每日应输出至少：

1. 玩家净充提（若有）  
2. 投注冻结/解冻合计  
3. 结算赢付合计 / 收注合计  
4. 抽水合计（闲赢/庄赢分列）  
5. 红包备付金拨出 / 认额核销 / 在途期末  
6. 奖励发放合计  
7. 调账合计  
8. 异常清单（重复录入、结算失败、短款、姓名匹配失败）  

勾稽关系（简）：

```
期初玩家总可用+冻结 + 调账入 − 调账出 + 奖励
 + 充值 − 提现
 + 庄闲内部转移（应轧差为 0）
 − 抽水出
 = 期末玩家总可用+冻结
```

红包账单独勾稽：

```
期初在途 + 本日拨出 − 本日核销 − 本日损失调整 = 期末在途
```

## 9. 与红包脚本的边界

| 模块 | 负责 |
|---|---|
| 红包脚本 | 是否创建、创建多少、发到群、超时取消 |
| 备付账 | 拨出/在途/核销 |
| 认额 | 后台录入确认写入 claim |
| 结算引擎 | 只读 claim + 注单，计算中奖并写赌资账 |

禁止：用红包面额直接加减玩家可用余额作为「赢钱」。

## 10. 最大赔付预留上线顺序（强制）

`reserved_cents` 与旧版本下注服务不具备双向滚动兼容：新版本创建的注单可能冻结 17 倍预留，而旧实例只会按 `amount_cents` 释放本金。上线本迁移时必须：

1. 暂停开新局并停止全部旧版 API、WebSocket 与后台 Worker，等待正在执行的事务结束。
2. 执行 `20260815213500_bet_liability_reserve` 数据库迁移；历史注单按原实际冻结本金回填。
3. 部署同一版本的新 API 与 Worker 后再恢复开局。

禁止新旧下注/结算实例并行处理同一数据库，否则可能遗留无法自动释放的冻结余额。
