# 至尊牛牛 — 系统架构说明

> 对应 PRD 第 3 章；描述用户侧与你们侧的完整结构。  
> **v1.9**：对局场地确认为 Mini App 网页实时游戏房；Telegram Bot 仅入口与私聊通知。

---

## 1. 总架构

```
┌──────────────────────────── 玩家侧 ────────────────────────────┐
│  Telegram App                                                   │
│    ├─ Bot 私聊（入口 / 实名奖励公告推送 / 菜单「进入游戏厅」）    │
│    └─ Mini App 游戏厅                                           │
│         ├─ 准入 + 四 Tab + 设置中心（支付密码 / 设备 / 协议）      │
│         ├─ 至尊牛牛互动群（网页群聊：竞庄/下注/聊天/抢包/成绩单）   │
│         └─ 跳转 Touch n Go eWallet（领取红包）                   │
└───────────────────────────────┬────────────────────────────────┘
                                │ Telegram Bot API / HTTPS / WSS
┌───────────────────────────────▼────────────────────────────────┐
│ 你们侧                                                          │
│  Nginx                                                          │
│    ├─ Mini App 静态资源                                         │
│    ├─ 管理后台静态资源                                          │
│    └─ 业务 API + 游戏房 WebSocket                               │
│         ├─ 用户 / 设备会话 / KYC / 支付密码 / 银行户口            │
│         ├─ 钱包 / Ledger                                        │
│         ├─ 局引擎 / 结算引擎                                    │
│         ├─ 房间实时中心（roomHub）                               │
│         ├─ 推送服务（Bot 私聊）                                  │
│         ├─ TNG 红包登记 + 认额录入（姓名匹配确认）                │
│         └─ Admin API（JWT）                                     │
│  Workers：推送 / 结算 / 倒计时扫阶段                              │
│  PostgreSQL + Redis + 队列                                      │
└───────────────────────────────┬────────────────────────────────┘
                                │
        TNG eWallet（发包账号 App 内创建 Money Packet；
        领取明细由运营对照录入，无对外 API/回调）
```

## 2. 玩家路径

```
邀请链接（ref_UID 自动填）
  → 当前默认 Bot /start
  → Mini App
  → 绑定邀请人 → 绑定设备
  → 直接进入大厅 / 钱包 / 聊天 / 我的
  → 首次点击钱包 → 实名+银行户口
  → 后台审核通过（Bot 私聊推送）→ 强制设置六位支付密码
  → 解锁钱包与对局；提现/玩家群红包由服务端验密
  → 大厅「至尊牛牛」/ 消息「互动群」→ 进入网页互动群
  → 群内竞标/下注/聊天 → 系统发 TNG 领取入口 → 抢包
  → 后台认额录入（姓名匹配）→ 系统计算中奖入账 → 群内成绩单
```

---

## 3. 一局数据流

```
凑人 → 竞标（冻庄池）→ 下注（冻注码）
  → 后台红包脚本创建 TNG 包（备付金→在途）
  → 网页房推送领取入口 → 玩家点开 TNG
  → 后台认额录入并确认（核销在途，写 claim）
  → 结算引擎算牌型与中奖（赌资账 + 抽水）
  → 房内成绩单 + 流水；达成就则奖励入账 + Bot 私聊推送
```

---

## 4. 运营侧路径

```
浏览器登录管理后台
  → 从游戏目录选择 gameCode
  → 在单游戏运营中心改规则配置 / 奖励 / 排行榜 / 虚拟玩家
  → 运营该游戏唯一互动群（最低人数 / 启停；名称由游戏目录固定）
  → 控制红包脚本（自动/半自动）
  → 监控对局、取消异常局、补认额
  → TNG 对账、调账、报表
  → 管理多个 Telegram Bot 并切换默认入口（仅入口与私聊通知）
```

当前游戏目录只有 `SUPREME_NIUNIU（至尊牛牛）`，因此数据库和后台只暴露一个至尊牛牛互动群。未来新增互动群不是复制 Room，而是先接入新的游戏代码、规则配置命名空间、状态机与结算引擎，再建立该游戏唯一的互动群。

## 5. Bot 与游戏房职责边界

```
Telegram Bot
  ├─ /start + Menu Button → 打开 Mini App
  ├─ 私聊推送：实名 / 奖励 / 公告 / 充提
  └─ 不再：群内指令解析、群禁言、群成绩单

Mini App 网页游戏房（WebSocket）
  ├─ join / leave / presence
  ├─ 竞标 / 下注 / 撤回 / 续庄
  ├─ 房内聊天 / 系统阶段播报
  ├─ TNG 领取入口（资格校验后下发 URL）
  └─ 成绩单展示
```

## 6. 多 Bot 路由

  ├─ Mini App initData 验签用对应 token
  └─ users.last_bot_id 决定私聊推送到哪只 Bot

## 9. 支付密码与设备会话安全

```text
PaymentPin（账号级 1:1）
  ├─ HMAC(SENSITIVE_DATA_KEY, userId + PIN) → bcrypt cost 12
  ├─ 连续失败 5 次 → locked_until +15 分钟
  ├─ is_set + 单调 version：重置保留凭证行，旧授权不可复活
  ├─ PostgreSQL 行锁串行化验密、改密、重置与资金确认
  └─ 只向客户端返回 set / lockedUntil，不返回 hash

受保护资金请求
  ├─ 先查询 requestId：同参数重放直接返回原结果
  ├─ requestId 按 UID 持久化，WebView 重开后继续复用
  ├─ 新请求验证支付密码
  └─ 资金事务复核凭证 version 后才创建业务单并写 Ledger

Device.authVersion
  ├─ 写入用户 JWT 的 deviceVersion
  ├─ HTTP 与 WebSocket 均校验 deviceId + authVersion
  └─ 后台解绑/重置时递增，并跨实例关闭旧 WebSocket
```

首次绑定设备时 JWT 使用初始 `authVersion=1`；设备为 `UNBOUND` 时只允许 `/api/me` 与准入绑定接口，不能访问钱包或游戏资金接口。后台重置支付密码由 SUPER/REVIEWER 执行，必须填写原因并写 `audit_logs`；重置事务将 `PaymentPin.isSet=false` 且递增版本，重新设置时在原行继续递增。

## 10. 按游戏隔离的运营命名空间

`gameCode` 是稳定的运营主键，`roomId` 只是该游戏当前唯一互动群的标识。新游戏必须先在 `gameCatalog.ts` 接入规则引擎、状态机与结算实现，后台不能直接创建未接入引擎的游戏。

```text
gameCode
  ├─ GameConfig (gameCode, key)              结构化配置、消息模板
  ├─ GameRuleDocument (gameCode unique)      纯文本玩家规则、草稿/发布版本
  ├─ RewardConfig (gameCode, code)           奖励任务
  ├─ DailyHandProgress (gameCode,user,date)  每日奖励进度
  ├─ Leaderboard (gameCode,type,period,key)  榜单快照
  ├─ TurnoverDaily (gameCode,user,date)      有效流水
  └─ RebateSettlement (gameCode,user,date)   返水结算
```

- 游戏配置缓存键使用 `gameCode:key`，小助手开关和消息模板先由 `roomId` 解析对应 `gameCode`。
- 开局时将当前游戏配置冻结到 `Round.configSnapshot`；后台保存只清理该游戏缓存并影响后续新局，进行中局不回读新配置。
- 奖励条件、每日进度、份数和发放按游戏查询；同一用户同一天可在不同游戏拥有独立进度。
- 积分榜按目标游戏房间内已结算的有效下注流水计算，不读取平台钱包余额；榜单快照和发奖幂等键均包含 `gameCode`。
- `withdraw` 等钱包/提现配置使用 `PLATFORM` 范围，不随游戏切换。

主要接口边界：

```text
Admin:
  GET/PUT /api/admin/games/:gameCode/config
  GET/PUT /api/admin/games/:gameCode/rules
  /api/admin/games/:gameCode/rewards*
  /api/admin/games/:gameCode/leaderboards*

Player:
  GET /api/game/rules?gameCode=
  GET /api/rewards?gameCode=
  GET /api/leaderboards?gameCode=
```

玩家页面使用 `/game/:roomId/rewards` 与 `/game/:roomId/leaderboards`，由大厅/房间状态取得 `gameCode`。旧的全局深链仅负责重定向到默认至尊牛牛，不能在后续请求中丢失游戏上下文。
