# 07 · 按局数利润池与代理称桶后台

> 依据《后台称桶操作.docx》实现。正式发放口径已经从“按马来日”切换为
> **按房间 + 开始局数 + 结束局数**。旧 `ProfitPoolDaily` 仅保留历史查询和上线切换用途，
> 不再自动生成，也不能与新批次同时待发。

---

## 1. 唯一财务口径

每个利润池只计算一个房间内连续、已结束的局号区间：

```text
公司总流水 = 区间内真人闲家有效流水 + 真人庄家有效流水
总抽水     = 闲家赢抽水 + 庄家盈利抽水
公司支出   = 公司总流水 × 本批支出百分比（四舍五入到分）
最终利润池 = 总抽水 − 公司支出
```

- 金额全程使用 `BigInt` 分，百分比以基点保存：`1% = 100 bps`。
- 虚拟玩家自身不计闲家流水；真人庄家仍沿用游戏结算口径，按该局全部有效对赌注累计庄家流水。取消局流水和抽水为 0。
- 闲家赢抽水读取每局 `Settlement.rakeCents`（outcome=PLAYER_WIN）；庄家盈利抽水读取成绩单 `bankerSummary.rakeCents`（旧局无此字段时仍累加 `Settlement.rakeCents` 中 BANKER_WIN 的历史值）。
- 支出百分比是每次生成批次的必填项，范围 `0–100%`，不是后台静默套用的日结默认值。
- 最终利润池 `≤ 0` 时生成 `NO_DISTRIBUTION` 批次，不转账、不向下一批结转。
- 最终利润池 `> 0` 时，代理份额按第 4 节计算，未分完的金额全部归公司留存。

## 2. 后台四步结算

后台「利润池 → 新建结算」严格按以下步骤执行：

1. **选择范围**：选择房间、开始局数、结束局数。
2. **输入支出**：填写本批公司支出百分比。
3. **预览核对**：展示流水、两侧抽水、支出、净池、代理分配、公司剩余点数和利润，
   并逐代理列出自身流水/团队流水、自身利润、下级差额利润和合计。
4. **二次确认生成**：服务端在 `Serializable` 事务内重新计算；预览指纹不一致则拒绝，
   一致后生成唯一编号并永久锁定所有局。

批次编号格式为 `TBYYYYMMDDNNNN`。正式生成后：

- 净池 `> 0`：状态为 `PENDING`，等待独立的「确认发放」操作。
- 净池 `≤ 0`：状态为 `NO_DISTRIBUTION`。
- 已生成批次不可删除、不可释放局锁、不可改财务数据；需要修正时应另做审计调整，不得覆盖历史。

## 3. 局数范围和永久锁

生成前必须同时满足：

- `startSeqNo ≤ endSeqNo`，单批最多 10,000 局。
- 范围内局号连续，不允许缺号。
- 每局必须是 `FINISHED` 或 `CANCELLED`。
- 不得早于旧日结切换边界 `ProfitPoolCutover.maxSeqNo`。
- 任意一局不得已存在于 `ProfitPoolRoundLock`。

数据库提供三层防重：

1. `roundId` 唯一；
2. `(roomId, seqNo)` 唯一；
3. PostgreSQL `EXCLUDE USING gist` 禁止同一房间的局号区间重叠。

因此即使两个管理员并发确认，最多一个事务可以成功。

## 4. 代理树与 130 点差额制

### 4.1 代理关系

- `Agent.parentAgentId` 支持任意层级，不限制二级、三级深度。
- 一个真人最多有一个代理身份、一个直属代理归属。
- 后台可建立一级代理、绑定或解绑玩家、启停代理、调整占成。
- 上级可把直属玩家升级为下级代理。
- 上级必须保留 `minReservePoints`；下级点数不能高于 `上级点数 − 最低预留`。
- 循环父子关系、跨线越权和不合法点数由服务端拒绝。

### 4.2 分成公式

```text
自身利润 = 最终利润池 × (自身流水 ÷ 公司总流水) × (自身点数 ÷ 130)
差额利润 = Σ 最终利润池 × (直属下级团队流水 ÷ 公司总流水)
                     × ((自身点数 − 下级点数) ÷ 130)
代理所得 = 自身利润 + 差额利润
```

- 自身流水 = 直属玩家流水 + 未归属到其他代理的代理本人流水。
- 团队流水 = 自身流水 + 所有深度下级的团队流水。
- 上级只赚直属下级的点差，不重复领取下级完整占成。
- 金额以分向下取整；取整差额和未分配点数对应利润归公司。
- `DISABLED` 代理本批金额为 0，但其团队流水仍向上汇总。

公司报表只列代理，不把玩家混入公司分配表；玩家归属和贡献保存在单独快照中。

## 5. 不可变历史快照

正式生成时保存：

| 模型 | 固化内容 |
|---|---|
| `ProfitPoolBatch` | 房间/局范围、流水、两侧抽水、支出、净池、130 基准、公司留存、状态和计算指纹 |
| `ProfitPoolRoundLock` | 每局 ID、局号、结束状态和结束时间 |
| `ProfitPoolAgentSnapshot` | 全量代理父子关系、用户、标签、状态、点数、直属/团队人数、流水、利润及差额明细 |
| `ProfitPoolPlayerSnapshot` | 当时的玩家归属、来源、流水和按直属代理点数折算的利润 |

历史报表、代理历史看板和 CSV 导出全部读取快照。之后改名、改点数、换上级、转移玩家，
都不会改变旧批次。

## 6. 发放、幂等和审计

`PENDING → DISTRIBUTED` 是独立且不可逆的资金动作：

- 状态比较并交换和所有钱包转账在同一个 `Serializable` 事务内完成。
- 每名代理使用唯一幂等键 `profit-share:{poolCode}:{agentId}`。
- 资金从 `PLATFORM_PROFIT_POOL` 转到代理 `USER_AVAILABLE`。
- 重复点击、请求重放或并发发放不会重复入账。
- 生成、发放、旧日报清理均与资金/数据动作在同一个事务内写入审计日志；
  审计失败会回滚整个动作。代理配置变更同样记录后台审计。
- 发放成功后向每名有金额的代理推送批次号、局号范围、占成和到账金额。

## 7. 完整后台

### 7.1 结算与报表

- 新建结算四步向导。
- 批次报表：公司账、130 点、公司剩余点数/比例/利润、代理树明细。
- 历史中心：按编号、状态、房间筛选；可回放任意快照，并分页展示只读的旧按日历史。
- CSV 导出使用 UTF-8 BOM，可直接用 Excel 打开。
- 若数据库被人工恢复出旧版 `PENDING` 日报，后台会显示阻断警告；正常部署会在迁移
  开始前强制要求这些日报全部确认或删除。

### 7.2 代理指挥大屏

- 实时模式展示整棵代理树；可搜索 UID/昵称/标签、折叠分支和全屏。
- 每个节点显示占成、直属/团队代理数、直属/团队玩家数、团队在线人数、累计利润和最近批次利润。
- 可切换任意历史批次，树结构和指标立即回放为当时快照。
- 点击代理打开专属侧栏：累计利润、可分页的批次趋势、直属下级、可分页的直属玩家和在线状态。

在线状态不复用 `Agent.status`。WebSocket 节点每 30 秒批量更新连接用户的
`RoomMember.lastSeenAt`，90 秒内有心跳视为在线，可在多实例部署中汇总。

### 7.3 代理专属看板

代理端 `/agent/report` 只允许当前启用代理访问：

- 顶部显示本人点数、直属代理数、全部团队代理数、直属/团队玩家数和累计已发利润。
- 可选择任意利润池批次，查看本批自身利润、点差利润、合计利润和团队贡献。
- 直属下级列表显示点数、团队人数、团队流水及本批差额贡献。
- 直属玩家列表显示 UID、归属来源、本批流水和利润。
- 历史批次和直属玩家均使用游标分页，可继续加载而不是截断在固定条数。
- 历史数据来自快照，代理只能看到自己和自己的直属数据；接口不返回公司的总流水、
  总支出或最终净池。
- 累计已发利润同时汇总切换前旧 `SETTLED` 份额与切换后的 `DISTRIBUTED` 快照。

## 8. 配置

平台配置存于 `GameConfig(scope=PLATFORM, key=profitPool)`：

| 配置 | 默认值 | 作用 |
|---|---:|---|
| `bucketBase` | 130 | 称桶总点数 |
| `minReservePoints` | 5 | 每级必须保留的最少点数 |
| `expenseRatio` | 2.5% | 向导默认提示值；正式结果以本批输入并快照的 `expenseBps` 为准 |
| `tierPresets` | 50 / 60 / 65 / 70 | 后台设点快捷预设 |
| `autoSettle` | false | 新版禁止日结自动生成 |

调整配置只影响以后生成的批次；已生成批次使用自己的快照值。

## 9. 上线迁移

迁移 `20260819030000_profit_pool_round_batches` 会：

1. 在同一数据库事务内锁住旧日报/份额写入并执行 `PENDING` 预检，再创建批次、
   局锁、代理快照、玩家快照、切换边界和编号序列表；触发器安装完成后才释放写锁。
2. 根据旧 `SETTLED/NO_DISTRIBUTION` 日报实际覆盖的 `Settlement.createdAt`
   （并以 `Round.settledAt` 防御跨午夜流水归日）为每个房间建立最大局号切换边界。
3. 保留旧日报和旧代理份额作为只读历史；数据库触发器阻止两张旧表的新增、修改和
   任意删除，仅为人工修复数据库后出现的 `PENDING` 保留受控删除通道。
4. 为利润池金额等式、非负金额、快照合计和发放上限建立数据库 `CHECK` 约束。

上线顺序：

1. 备份数据库，并在旧版本仍可运行时处理所有 `PENDING` 日报：应付款的先确认，
   未付款的确认无转账后删除。
2. 执行 Prisma migration；若仍有任何 `PENDING`，迁移会在创建新表前直接失败。
   迁移成功后旧版本实例即使仍短暂运行，其旧日结写入也会被数据库拒绝。
3. 核对每个房间的 `cutoverSeqNo` 和下一可用局号。
4. 用少量已结束局做预览，核对流水、抽水和支出。
5. 生成首个正式批次，确认局锁和快照后再发放。
